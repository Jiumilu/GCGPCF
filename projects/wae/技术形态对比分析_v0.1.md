# WAE 技术形态对比分析 v0.1

日期：2026-10-12　状态：**draft（供老卢裁定）**
用途：为「世界资产浏览器（WAE）」统一界面框架项目在 **共享包 monorepo** 与 **微前端容器** 两种技术形态之间提供决策依据。

---

## 0. 一句话差异

| 形态 | 机制 | 本质 |
|---|---|---|
| **共享包 monorepo** | 框架抽成私有 npm 包，各项目**在自己的仓里引用**；壳是**共享代码** | 统一的是**代码资产**；各项目仍是独立应用 |
| **微前端容器** | 一个主壳**运行时**动态加载各子应用的 bundle 并挂载 | 统一的是**运行时容器**；各项目成为子应用 |

---

## 1. 十二维对比

| # | 维度 | 共享包 monorepo | 微前端容器 | 胜出 |
|---|---|---|---|---|
| 1 | 统一程度 | 令牌/组件/外壳代码/骨架全统一；路由与应用生命周期各自独立 | 外壳/路由/导航/状态真正统一，一个浏览器打开全部 | 微前端 |
| 2 | 技术栈兼容 | **仅 React 家族**（WAME/PKC/Brain/PVAOS）可直接受益；Vue/Next 只能共享令牌 | wujie/qiankun 可接 React+Vue；**Electron 桌面端无法纳入**；Next 需改造 | 微前端（略） |
| 3 | 各项目改造量 | **小–中**：替换 import、套统一壳、复用量令；不动构建与路由 | **大**：每个子应用改入口、暴露生命周期、样式隔离、store 冲突处置 | 共享包 |
| 4 | 独立运行（"先单独运行"） | ✅ 框架仓本身即独立可运行应用（演示/自检模块） | ✅ 主壳独立运行，子应用也各自独立运行 | 平 |
| 5 | 渐进纳入 | ✅ 天然渐进：项目可锁版本、可灰度、可回退 | ⚠️ 渐进但每个子应用都需一次性完成微前端改造 | 共享包 |
| 6 | 性能/首屏 | ✅ 无额外运行时开销，按项目自身构建优化 | ⚠️ 主壳需加载子应用运行时，首屏与内存开销更高 | 共享包 |
| 7 | 构建/发布复杂度 | ✅ 标准包发布（版本化），各项目自建自发布 | ⚠️ 需维护主壳版本矩阵 + 子应用兼容矩阵，联调链路长 | 共享包 |
| 8 | 可调试性 | ✅ 各项目独立调试，栈追踪完整 | ⚠️ 沙箱内调试困难，错误跨越边界 | 共享包 |
| 9 | 隔离性/独立部署 | ✅ 完全独立部署，互不影响 | ⚠️ 运行时耦合，一方异常可能影响主壳 | 共享包 |
| 10 | 状态/数据共享 | 需各项目自行对接（无强制通道） | 主壳可提供统一状态通道（也是耦合风险源） | 微前端 |
| 11 | 与 GPCF 规范契合 | ✅ 高：分层复用 + 例外机制天然对应 | ⚠️ 中：需新增"容器级"例外与门禁口径 | 共享包 |
| 12 | 一次性总成本 | **低–中** | **高**（且对 Electron/Vue/Next 仍无法全覆盖） | 共享包 |

**机械计分：共享包 8 胜 / 微前端 3 胜 / 1 平。**

## 2. 逐项目适配判断

| 项目 | 技术栈 | 共享包 monorepo | 微前端容器 |
|---|---|---|---|
| WAME | React（母本） | ✅ 直接受益（抽包后反向引用） | ✅ 可作子应用 |
| PKC | React（同构） | ✅ 首选受益 | ✅ 可作子应用 |
| Brain | React（同构，布局异） | ✅ 受益 | ✅ 可作子应用 |
| PVAOS | React（历史仓） | ✅ 受益（需迁移清理） | ✅ 可作子应用 |
| GFIS/GPC/MMC/AAAS/ICP/SOP | 无前端 | ✅ 新页面直接建在共享框架上 | ➖ 无子应用可挂 |
| Studio/XiaoG | Node web-ui | ⚠️ 仅令牌映射 | ⚠️ 需大幅改造 |
| PQC | Next.js | ⚠️ 仅令牌映射 | ⚠️ 需改造 |
| SpaceAI Platform | Vue3 | ⚠️ 仅令牌映射（另有一套 ui-kit） | ⚠️ 需适配桥 |
| XGD/XiaoC | Electron | ❌ 无法纳入 | ❌ 无法纳入 |

**关键结论**：微前端主打"一个容器装全部"，但本项目群里 **Electron 两个项目注定装不进去、Vue/Next 三个项目需大改造**——"全部"这一最大卖点在本项目群**无法兑现**；而共享包能覆盖 React 家族 + 无前端新页面（合计 9 个项目群成员）。

## 3. 成本量级（相对估算，非承诺工期）

| 项 | 共享包 monorepo | 微前端容器 |
|---|---|---|
| 框架抽取 | 中（外壳解耦 + 令牌收口 + 组件组） | 中（主壳 + 沙箱 + 通信层） |
| 每项目接入 | 小（PKC/Brain）～中（PVAOS） | 大（每项目 1 次性微前端改造） |
| 异构项目 | 令牌映射即可 | 需适配桥或直接放弃 |
| 长期维护 | 低（版本化包） | 中–高（版本兼容矩阵） |
| 风险等级 | 低 | 高 |

---

## 4. 风险对照

| 风险 | 共享包 | 微前端 |
|---|---|---|
| 样式/依赖冲突 | 低（各自构建） | 高（运行时共享 DOM/全局） |
| 版本并行失控 | 低（可锁版本） | 中–高（主壳/子应用矩阵） |
| 抽取导致 WAME 回归 | 中（需全量回归） | 中–高 |
| 覆盖不全 | 已接受（只覆盖 React 家族 + 新页面） | **无法覆盖全部（卖点落空）** |
| 调试困难 | 低 | 高 |

## 5. 推荐路线

### 推荐：**以共享包 monorepo 为基座，微前端仅作"异构项目过渡嵌入"的可选手段**

分三步走：

1. **第一步（现在，P0–P2）：共享包 monorepo**
   建 `@globalcloud/ui-tokens` / `ui-kit` / `app-shell` / `app-registry`，框架仓独立运行；WAME 反向引用，PKC/Brain/PVAOS 逐步接入。**风险最低、见效最快、可回退。**

2. **第二步（P3）：统一入口注册**
   `AppSwitcher` 泛化为全项目群"应用切换器"——同构项目直接跳转统一壳内模块；异构项目（Vue/Next/web-ui）以**受控 iframe 嵌入**（非 Module Federation）实现"一个入口打开全部"，成本远低于完整微前端。

3. **第三步（可选，按需）：微前端试点**
   只有当"统一运行时"成为刚性需求时，才在 1–2 个项目上试点 Module Federation/wujie。**不预设、不一上来就做。**

> **不推荐**直接上微前端容器：投入最大、风险最高，而最大卖点（装下全部项目）在本项目群因 Electron/Vue/Next 的存在而无法兑现。

---

## 6. 如何验证选型正确（可验真流程）

1. **共享包验证**：框架包独立 `dev` 可启动 + 单元测试通过；PKC 引用后跑通登录/主列表一轮，留 UI gate 证据（截图 + innerText 断言）。
2. **统一入口验证**：应用切换器可真实跳转/嵌入 3 个以上项目，留真实运行证据。
3. **反向不成立验证**：若第 2 步发现 iframe 嵌入不满足需求，再评估微前端，届时以真实证据触发，而非预设。
4. 全程按 GPCF UI gate 记录 `Tool route / Context package / Design options / Selected option / evidence`。
