# GlobalCloud 项目群 Codex-DSH-Hermes 协同开发与运行方案

## 1. 定位与适用边界

本方案定义项目群的目标协同模式：**Codex 统筹治理和架构，DSH（DeepSeek Harness）负责具体开发与测试，Hermes 作为产品 AI 能力运行中心，负责 Agent 执行、AI 运行观测和诊断，并在各项目提供遥测后逐步汇集项目运行信息。** GPCF 是任务、状态、证据和方案传导的控制载体；Harness Governance、WAME 和人工责任人继续履行独立审核、授权与验收职责。

三方协同采用**自动交接为主、关键决策和高风险动作由人工确认**的目标模式。自动化负责生成任务、传递回执、归集证据、检查门禁和上报异常；自动化是否可用必须按试点真实验证，不因本方案写入而视为已接通。

适用范围为 GPCF 当前纳管的项目及后续按项目群规则纳入的项目。各项目既有业务事实主账、知识正本、治理权限和环境边界保持其主责。本方案规定目标分工和落地路径；文档完成不表示 DSH 或 Hermes 集成已完成，也不表示任何项目真实运行、集成、交付或验收通过。

“所有项目的 AI 能力基于 Hermes”是**目标接入原则**，范围为项目向业务用户或内部产品流程提供的模型调用、Agent 执行、工具调用及运行回执。当前项目群尚未全量接入；各项目既有直连路径须登记、评估、迁移或明确受控例外，不因本文发布而视为已经统一。Codex 与 DSH 自身使用何种开发模型或客户端属于工程工具链选择；如需强制经 Hermes 调用，须单独验证并纳入后续契约。

本方案继承 `01-architecture/GlobalCloud 项目群总体方案.md` 与仓库根目录的 `GlobalCloud 项目群实施方案.md`。涉及现有 XiaoC 模型路由、Brain 知识服务和 XiaoG/Hermes 命名的职责差异，按第 8 节完成双主方案与项目级方案传导；传导和接口验证前，不把目标结构写成已落地事实。

## 2. 责任与决策权

| 主体 | 主责 | 交付或回执 | 权限边界 |
| --- | --- | --- | --- |
| Codex | 项目群评估、优先级建议、总体方案与架构维护、跨项目依赖分析、Feature 派发、冲突处理和状态收口 | 受控任务包、架构决策记录、影响分析、状态与阻塞记录 | 重大业务决策、生产发布和验收状态须按既有人工授权链确认；不得以计划代替仓库证据 |
| DSH | 在指定项目仓和范围内实施开发、测试、修复与自检 | 代码变更、测试和构建记录、可重放证据、已知问题与回滚信息 | 不自行裁决 `accepted`、`integrated` 或 `production_ready`；不得越过任务包修改其他项目或生产环境 |
| Hermes | 运行产品 AI 能力、Agent 和自身网关；按接入契约汇集项目遥测、发现异常并提出诊断建议 | 能力与接口版本、调用及 Run 回执、已接入范围内的健康指标、异常和恢复观察 | 不取得业务事实主账、知识正本、治理审批权或生产基础设施变更权；未接入项目不得称为已监控 |
| Hermes 平台 owner / 值守人员 | 对 Hermes 服务可用性、容量、告警接收、故障恢复及凭据轮换负责 | 值守表、告警确认、恢复与回滚记录 | 生产操作仍遵守现有人工授权边界；不得把 Agent 的诊断建议当作操作授权 |
| 项目 owner / 值守人员 | 对本项目业务服务、客户影响、非 AI 路径及项目遥测负责 | 项目健康与影响判断、降级和恢复回执 | 保留项目业务主责；不得把自身服务故障转嫁给 Hermes |
| 项目群统一主值守 | 用户本人（`lujunxiang`）接收 Hermes 平台及纳管项目告警，完成初步分诊与转派 | 告警接收、确认、转派及升级记录 | 值守身份不自动取得项目业务决策权或生产操作权限；各项目与平台 owner 仍承担各自恢复责任 |
| GPCF | 保存 Feature、队列、角色流转、文档、证据及门禁的唯一项目群控制记录 | `feature.yaml`、`journal.md`、`evidence/`、`runtime/queue.json`、`runtime/logs/` | 不把自动检查通过解释为真实业务验收或客户接受 |
| Harness Governance / WAME / 人工责任人 | 独立核验证据、执行治理授权与状态裁决 | 审核结论、授权记录、人工确认 | 执行方不能自审自批；高风险动作按现有权限规则办理 |

Codex 是管理角色，GPCF 是受控记录与门禁体系；两者不建立第二套相互竞争的项目状态。DSH 的测试是交付证据，Hermes 的健康回执是运行证据，Harness 的审核是独立判定，人工确认是需人工批准状态的入口。Codex、DSH 和 Hermes Agent 都不能代替具名值守人员承担持续响应责任；项目或平台没有主责人与替补时，不得进入正式运行接入。

用户于 2026-10-18 确认由本人担任项目群统一主值守。此确认只确定第一接警人与分诊责任；替补人员、值守时段、实际告警通道及各项目和 Hermes 平台的恢复操作人仍须在 P0 登记并验证。替补未确定前，不宣称具备全天候或持续运行保障。

## 3. Hermes 能力边界与接入架构

目标架构要求纳管项目的产品 AI 调用经 Hermes 的版本化能力接口进入。各项目保留自身业务流程、数据主责和用户界面；Hermes 提供调用入口、Agent 运行、受限工具执行及 AI 运行回执。对项目服务的监测以项目提供的遥测为输入，由项目 owner 对服务事实负责；Hermes 负责关联、提示和只读诊断。具体接口、成本与观测能力均以逐项目试点结果为准。

### 3.2 能力分层与项目接入

| 层次 | Hermes 目标能力 | 接入条件与责任边界 |
| --- | --- | --- |
| AI 调用与执行 | 对话、流式响应、Agent Run、会话续接、工具执行和结果回执 | 按项目和用途选择契约；XGD 等依赖原生 `tool_calls` 的链路须验证 Run 适配，不能只替换模型 API 地址 |
| 能力目录与质量 | 能力 ID、版本、消费者、评测集、调用成功率与升级前后对比 | MMC 保留模型与治理配置主责；Hermes 提供运行目录和实测结果，不单独裁定业务质量 |
| AI 运行观测 | 关联项目、环境、能力版本、Feature ID、请求 ID、Run、错误、延迟及用量 | 仅把真实采集的字段写为运行证据；费用须与账单或供应商数据对账 |
| 项目运行诊断 | 汇集项目 owner 提供的健康指标与事件，关联 AI 故障、服务故障和恢复观察 | 项目服务仍负责自身遥测、值守和修复；Hermes 只读诊断，不代替基础设施监控或生产变更执行者 |

按项目保留接入清单，至少记录 AI 消费者、当前路径、目标接口、Profile/凭据、允许工具、数据范围、运行环境、监控来源、降级方式、责任人和验证状态。状态只使用 `未盘点 / 待适配 / 试点中 / 已验证接入 / 受控例外`，并附证据位置；不得以代码中存在 Hermes URL 代替 `已验证接入`。

### 3.3 运行拓扑与产品边界

项目界面通过本项目服务端适配器调用 Hermes 的项目级 Profile；Hermes 执行 AI 请求并返回结果与 Run 事件。项目服务保留业务授权、数据过滤、超时和降级责任。Studio 是 Hermes 的界面与局部运维入口；Hermes 工作体系提供规则和报告模板，均不自动等于 Hermes Agent 的项目群监控服务。AI 与项目服务的观测事件按契约关联到 GPCF Feature，GPCF 只引用证据并运行确定性门禁，不依赖 Hermes 在线才能复核历史证据。

| 相邻系统 | 与 Hermes 的目标关系 | 保留的主责 |
| --- | --- | --- |
| KDS | 通过授权引用提供知识来源 | 知识正本及来源、版本和权限 |
| Brain | 提供知识检索、分析或工作台能力，按接口契约被 Hermes 调用或向其提供结果 | 知识服务及其产品界面；不替代 KDS 正本 |
| XiaoC / XGD / XiaoG | 既有 AI 能力、长程任务和轻量执行能力按能力清单与 Hermes 对接；入口、模型路由和运行所有权需逐项裁定 | 各自现有受控职责，在裁定前不静默迁移 |
| GCMEM | 提供授权范围内的长期记忆能力 | 记忆账本与 KDS 之间的既有唯一正本边界 |
| MMC / WAME | 为能力、工具和运行行为提供注册、权限与治理约束 | MMC 控制面配置；WAME 治理授权、审查与状态裁决 |

每个 AI 接入至少明确：调用方及租户身份、能力和契约版本、允许的数据与工具范围、来源引用、超时与重试、幂等要求、错误和降级方式、审计关联 ID、用量与成本责任人。项目服务端使用独立 Profile 与凭据，并按用途约束工具；不得向前端或其他项目下发 Hermes 默认密钥。涉及个人或敏感数据时按数据分级和最小权限授权；不得把提示、模型输出或 Hermes 记忆直接写成业务事实。

Hermes 故障时，项目应保留已定义的非 AI 核心路径或进入显式降级状态；禁止用未经授权的直连模型调用绕开统一入口。GPCF 的确定性校验脚本和已有证据应可离线复核，避免 AI 服务故障导致治理门禁不可用。

### 3.4 隔离、连续性与例外

每个项目按数据边界配置独立 Profile、服务端凭据、工具允许清单和用量配额；上线前至少验证错误项目凭据、越权工具、跨项目会话和跨项目记忆均被拒绝。独立 Profile 是隔离前提，不能单独证明隔离有效。凭据轮换、撤销和泄露处置须有平台 owner 与项目 owner 的共同回执。

Hermes 不可用或超出约定延迟时，项目适配器按已验证契约返回明确错误、超时或非 AI 降级结果，并记录请求 ID 与影响范围。业务确需临时直连 Provider 时，由项目 owner 提出范围和期限，经 MMC/WAME 对应策略及人工授权链批准后登记为受控例外；例外到期复核并回迁。恢复时核对未完成 Run、重试幂等与项目侧结果，避免重复执行工具或重复写入。

## 4. 单一 Feature 的交接协议

每项开发或修复工作使用一个 GPCF Feature ID 串联任务、代码、AI 契约、运行事件和证据。跨项目改动须列出各仓的主责与依赖；同一状态只在 GPCF 受控入口记录，外部工作台展示引用该状态。

| 阶段 | 发起方 → 接收方 | 最小交接内容 | 通过条件 |
| --- | --- | --- | --- |
| 任务定义 | Codex → DSH | Feature ID、目标仓和基线版本、允许改动范围、架构约束、验收标准、必跑检查、依赖、授权边界与回滚路径 | DSH 确认接收、范围和基线；不明确项退回 Codex 澄清 |
| 开发与自检 | DSH → Codex | 变更引用、受影响文件、测试环境与命令、真实结果、失败项、证据位置和遗留风险 | 变更可定位，证据可重放；失败不得写为通过 |
| AI 接入准备 | Codex → Hermes / 项目 owner | Feature ID、调用项目、能力契约与版本、Profile 和工具权限、遥测来源、失败降级和告警责任人 | 完成真实调用、跨项目隔离和观测验证；未确认时保持候选状态 |
| 运行接管 | Hermes 平台 owner ↔ 项目 owner | 值守人与替补、告警通道、服务目标、故障分级、回滚操作人和授权边界 | 双方确认告警可达、降级可执行；缺任一责任人时不得转入正式运行 |
| 独立核验 | Codex → Harness Governance | DSH 交付证据、Hermes 接入或运行证据、GPCF Evidence Gate 结果和阻塞清单 | Harness 独立审计；退回项由 Codex 派给 DSH 或接口主责方 |
| 运行反馈 | Hermes / 项目 owner → Codex | 关联 Feature/版本/环境的 AI Run、项目健康、错误、延迟、异常与恢复证据，注明采集来源 | Codex 分诊为运行故障、代码缺陷、契约问题或新需求，并登记下一责任人 |
| 状态收口 | Codex → GPCF / 人工责任人 | 审计结论、真实运行证据、未决风险、授权与确认状态 | 仅在满足对应状态门禁后更新；需人工确认的状态保持待确认 |

交接回执应有发送方、接收方、时间、Feature ID、输入版本、证据位置、结论和下一责任人。未收到接收确认或缺少关键字段时，任务保持原责任方名下并登记阻塞，防止无人负责的“已派发”。这些字段先记录在现有 `journal.md` 与 `evidence/` 中；试点证明必要后再修改 GPCF 数据结构。

### 4.1 自动交接与人工控制协议

以 GPCF Feature 为唯一工作标识和状态来源；项目 ID、Feature ID、任务包版本与运行关联 ID 贯穿 Codex、DSH、Hermes。自动化可传递任务和证据，不建立三套并行状态，也不把 Project/Plane 的协作投影写回为验收结论。每次流转由发送方写入现有 `journal.md` 或 `evidence/`，角色切换按 `gpcf_dispatch.py` 写入 `runtime/logs/F-xxx.jsonl`；接收方确认所接版本和范围后才改变责任归属。

| 场景 | 自动触发与交接 | 人工控制点或失败接管 |
| --- | --- | --- |
| 新需求、Feature 或开发缺陷 | Codex 在 GPCF 建任务包并派给 DSH；DSH 回传接收回执、代码引用、测试和失败证据；Codex 运行确定性门禁 | 范围或架构冲突由 Codex 裁定；DSH 未接收时责任留在 Codex，测试失败退回 DSH |
| AI 能力接入或版本变更 | Codex 提供项目身份、契约、权限和验收口径；DSH 完成适配测试；Hermes 返回实际调用、隔离和运行回执 | 权限扩大、凭据范围变化、受控例外和对外发布走人工授权；无真实调用回执不得标为已接入 |
| 运行告警或故障 | Hermes 对已接入范围自动采集并关联项目、Feature、请求或 Run；告警送达统一主值守本人，同时给 Codex 留存分诊输入 | 您确认接警并转派平台或项目 owner；代码缺陷交 DSH，生产恢复按现有授权边界；无人接收时保持未接管并升级告警 |
| 架构与跨项目契约变化 | DSH、Hermes 或项目 owner 提交影响证据；Codex 形成决策和传导任务，再派发实施与验证 | 架构、业务责任和兼容取舍由 Codex 按项目群治理链裁定；不得由执行工具静默改写主方案 |
| 发布、验收与状态提升 | Codex 自动归集 DSH 测试、Hermes 运行、项目结果及 Evidence Gate 结论，送独立审核 | 生产部署、共享配置与权限变更，以及 `accepted`、`integrated`、`production_ready`、`customer_accepted`，必须按人工授权和确认办理 |

自动交接至少校验：任务包版本与目标仓基线一致、接收方身份和范围明确、证据可定位、回执指向同一 Feature、下一责任人唯一。重复通知按同一 Feature、阶段和输入版本去重；超时或工具不可用时记录失败并有限重试，仍无有效回执则通知您和当前责任人，保持原责任方及原状态。恢复后先对账，再补写实际发生的回执，不伪造期间的接收或运行记录。

自动化的可执行范围限于普通本地任务派发、只读检查、证据归集、门禁计算和告警路由。高风险动作沿用人工授权；已批准的具体动作仍须记录目标、影响范围、执行者、结果与回滚。DSH 开发凭据由用户在 DSH 中单独配置，不能从 Hermes 现有密钥复制或默认继承。Codex、DSH、Hermes 任一方不可用时，项目 owner 与统一主值守依靠 GPCF 记录继续人工接管，恢复后再做版本和证据对账。

## 5. GPCF Feature 与门禁映射

GPCF 2.0 保持现有 Feature 最小目录和脚本入口。新工作优先经 `python scripts/gpcf_new_feature.py` 建立；调度经 `python scripts/gpcf_dispatch.py <FEATURE_ID>`，角色流转写入 `runtime/logs/F-xxx.jsonl`；证据门禁经 `python scripts/gpcf_check_evidence.py <FEATURE_ID>`；关闭经 `python scripts/gpcf_close_feature.py <FEATURE_ID>`。

| GPCF 角色或环节 | 主责映射 | 必需证据 |
| --- | --- | --- |
| Dispatcher / Planner | Codex | 目标、范围、依赖、验收和授权边界 |
| Builder / Repair | DSH | 实现差异、测试、构建与修复记录 |
| Evaluator | GPCF 自动门禁与独立 Harness 审核 | 本地可回放结果、独立审核结论 |
| Recorder | GPCF，由 Codex 按审核结果收口 | Feature、队列和日志一致，状态来源可追溯 |
| AI 运行与观测 | Hermes | 能力契约、运行回执、异常和恢复证据 |

Evidence Gate 对开发范围、测试、构建、lint 和运行证据分别判定。确实不适用的证据写 `waived` 并说明原因；不得以默认 `not_required` 掩盖缺失。`development_ready`、真实业务验证、人工验收、系统集成、生产就绪和客户接受保持分线；Hermes 健康或 DSH 测试通过均不得单独提升更高状态。

## 6. 运行监测与故障协作

Hermes 对 AI 运行记录至少关联能力版本、调用方、环境、请求关联 ID、时间、结果、延迟、错误类型与用量。项目 owner 输出服务健康、依赖失败、告警及恢复事件；Hermes 在已授权范围内进行关联和只读诊断。每个项目分别登记 `AI 调用可观测 / 服务健康可观测 / 告警可达 / 恢复可核验` 四项覆盖结果，缺一项不能笼统标记为“已监控”。

异常处理顺序为：Hermes 或项目 owner 发现并保存原始证据 → Codex 判断影响、优先级和主责 → DSH 修复代码或测试契约（若属于工程缺陷）→ 独立门禁复核 → Hermes 与项目 owner 分别观察 AI 与服务恢复 → Codex 在 GPCF 中收口。若问题属于数据、权限、外部依赖或生产基础设施，转交对应项目 owner 或人工授权链；不得机械地派给 DSH。

生产服务重启、配置热更新、部署、迁移、删除、权限变更、云账号及网络入口操作仍按 `02-governance/ops/ecs-access-control-and-network-boundary.md` 和项目群授权规则执行。Hermes 的诊断输出只作为证据或建议输入，不自动触发这些动作。

### 6.1 故障责任与接管

| 事件 | 首要接管人 | 协同与收口 |
| --- | --- | --- |
| Hermes API、Agent 或能力接口故障 | 统一主值守先接警并转派 Hermes 平台 owner | 项目 owner 判断业务影响并执行项目降级；Codex 协调优先级；DSH 处理经定位的代码缺陷 |
| 项目业务服务或遥测故障 | 统一主值守先接警并转派项目 owner | Hermes 提供已有 AI 运行证据；Codex 分诊跨项目影响；DSH 处理经定位的工程缺陷 |
| 越权调用、凭据泄露或数据边界异常 | 对应平台与项目 owner 共同接管 | 按既有安全授权链处置；Hermes 保全只读证据，Codex 记录影响与待决事项 |
| Codex 或 DSH 暂不可用 | 对应项目 owner 保持事件和任务主责 | 通过 GPCF 留存输入、证据与下一责任人；人工指定替补后继续，不把无人接收写为已交接 |

每个接入项目在运行前填定可用性与延迟目标、检测和确认时限、恢复与数据对账目标、告警渠道、值守人与替补。故障演练至少覆盖 Hermes 入口不可用、能力接口 500、请求超时、跨项目凭据误用和项目遥测中断；每项记录发现时间、接收人、降级、恢复与证据位置。没有运行目标、值守表或演练回执时，不宣称具备项目群运行保障。

## 7. 质量、可靠性和权限控制

1. **交付质量**：DSH 对单元、契约、集成或端到端测试承担任务包指定的实现责任；独立审核复核结果和范围。跨项目接口变更同时验证调用方与被调用方。
2. **单点依赖**：Hermes 统一入口须定义可用性目标、容量、限流、超时、告警、故障降级和恢复对账。试点未验证前不承诺项目群级 SLA。
3. **版本兼容**：能力接口、模型/Agent 配置、工具权限和知识引用使用可追溯版本；变更先列消费者并做契约兼容检查。
4. **最小权限**：Codex、DSH 和 Hermes 分别使用任务所需权限；Hermes 的项目级 Profile、密钥、工具集与网络入口须在扩大接入前验证。生产凭据、敏感数据、真实写入与对外发布遵守现有高风险人工授权边界。日志不得包含明文凭据或不必要的个人数据。
5. **成本归属**：Hermes 汇总 AI 用量和费用，关联项目、能力版本与 Feature；Codex 评估投入产出，异常消耗触发诊断，不自动牺牲必要的质量或授权检查。
6. **证据真实性**：设计文档、mock、fixture、内部测试、真实业务输入和生产运行证据分别标记；KDS 本地镜像不写成真实 KDS API 已同步。
7. **独立恢复能力**：Hermes 故障时，项目非 AI 核心路径与 GPCF 确定性门禁仍能工作；恢复后核对未完成任务、重复请求及业务结果。故障切换与回迁须有演练证据。
8. **责任连续性**：Codex、DSH 或 Hermes Agent 中断时，具名 owner 与替补接管；任务、告警和授权状态持久化于既有受控入口，不依赖单次 AI 会话记忆。
