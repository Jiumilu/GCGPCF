# GlobalCloud 项目群总体方案

## 1. 定位

本文是 GlobalCloud 项目群最高层总体控制性方案，负责项目群架构、术语、版本、兼容矩阵、方案传导、项目边界与协同控制。

## 2.1 GC-ICP 产业控制平面边界

GC-ICP 是项目群产业控制中枢候选项目，拥有产业建模、资源投影、场景评估和产业控制决策候选职责，但不拥有业务事实写入权、治理批准权或生产执行权。

| 相邻项目 | 主责保持 | ICP 禁止越权 |
|---|---|---|
| KDS | 知识主存和十一池事实索引 | 不建立第二套资源事实主账 |
| WAME | 治理、证据、状态和人工确认 | 不自动批准或晋升状态 |
| GPC | 平台订单和跨组织协同 | 不创建订单、运输或 POD 事实 |
| GFIS | 工厂生产、质量、库存和设备 | 不排产、放行或控制设备 |
| PVAOS | 租户、组织、伙伴和门户 | 不管理身份或生态主数据 |

ICP 当前状态固定为 `candidate/partial/human_required`，本地契约、API 和 fixture 验证不得解释为真实业务接入、项目群集成或生产就绪。

## 2.2 武汉城市圈绿色供应链运营 SOP 场景链路

武汉城市圈绿色供应链运营 SOP 是项目群首个按“运营在前、投厂在后、订单先行、本地协同”进入受控内部试运行的场景链路。该链路覆盖武汉、应城、咸宁、武穴和 N 地区五个任务单元，目标是在 2026-06-29 至 2026-07-05 首轮 7 天内部试运行中跑通统一订单池、G0-G8 轻量闸门、红黄灯清单、周评分和补证队列。

项目群职责边界如下：

| 项目 | 场景职责 | 边界 |
|---|---|---|
| SOP | 输出场景规则、模板、评分口径、硬否决项和周评分报告 | 不制造业务事实，不替代 owner 确认 |
| KDS | 作为客户、订单、主体、合同、交付、回款和会议材料的唯一知识事实引用源 | 未授权前只读，不执行真实 KDS API 写入 |
| GFIS | 承接 G5-G7 以后生产、质检、仓储、工厂出库和运行层主键 | 工厂出库回执不是客户 POD；无真实 source-of-record 时不得声明真实 SOP E2E |
| GPC | 承接订单池、红黄灯、运输、客户 POD、异常和周评分看板 | 客户签收须有客户或承运确认来源；不以页面可见替代业务闭环 |
| GPCF | 纳入项目群门禁、证据、状态矩阵、依赖矩阵和 LOOP 闭环 | 不替代业务 owner、WAME 或客户验收 |
| WAME | 承接授权、审查、越权控制和状态裁决入口 | 未经人工确认不得 accepted、integrated 或 production_ready |

该链路的总体定位是 `controlled_internal_pilot`。它可以作为项目群真实运营补证和系统开发任务的输入，不得直接声明正式 SOP 发布、客户验收、生产运行完成、项目群集成完成或 1+8 全覆盖已达成。

## 2.4 四业务体系（2026-10-25 CHG-14）

| 业务 | 买什么 | 收入来源 | 独立核算 |
|---|---|---|---|
| **平台** | 买入口 | SaaS 订阅（四档）+ 实施/集成 | ✅ |
| **供应链** | 买交易 | PVA 交易佣金（按销分佣）+ 供应商服务费 | ✅ |
| **FDE** | 买时间 | 企业 90 天项目 / 城市项目制 / 认证生态 | ✅ |
| **数据** | 买资产 | 数据服务与报告（首发）→ 资产化（后续） | ✅ |

四业务分开核算（不互相补贴掩盖亏损）；优先级：平台 + FDE → 供应链 → 数据（Q34–Q41/Q82–Q86）。

## 3. 总体架构原则

| 原则 | 控制要求 |
|---|---|
| 一个总控体系 | 项目群总体方案和项目群实施方案为双主控，所有项目方案必须继承 |
| 多个受控项目 | 每个项目只能有一个唯一总体方案和一个唯一实施方案 |
| 真实证据驱动 | 运行、集成、交付和验收必须绑定命令、证据、门禁和回滚边界 |
| 双向传导 | 项目群主方案变化传导到项目；项目方案变化回传项目群主方案并影响关联项目 |
| 不越权升级 | 未经人工确认，不得声明 `accepted`、`integrated`、`production_ready` 或 `customer_accepted` |

## 3.1 架构权威与三种视图

`GlobalCloud宪法` 是最高规范性权威；本文是项目群总体架构和项目边界的控制源；`GlobalCloud 项目群实施方案.md` 管真实执行和验收。`01-architecture/GlobalCloud项目群系统架构图.md`、总体架构迭代分析和专项架构是本文的派生视图。绿色供应链、WAS、知识工程、安防等专项只在各自领域细化，不得覆盖本文的跨项目主责。历史连接器名或旧缩写可为兼容保留，但不得据此恢复已停用的 WAES 项目身份。

| 视图 | 回答的问题 | 受控边界 |
|---|---|---|
| 业务架构 | 谁服务谁、价值如何产生、哪个项目拥有哪类业务事实 | 业务 owner 确认；不能由页面或 AI 推断事实 |
| 系统架构 | 哪些能力由哪些项目承载、经什么契约协作 | 逻辑能力与物理仓库分开；一个能力可跨项目，权威主账必须唯一 |
| 实施架构 | 哪个版本已运行、依赖和证据是否闭合 | 由项目群实施方案、Feature、Evidence Gate 和 live 状态裁决 |

设计目标、局部测试通过、真实运行、项目群集成和客户验收是不同状态；下文的目标接口均不自动表示已接通。

项目群研发与 AI 运行协作以 `02-governance/GlobalCloud项目群Codex-DSH-Hermes协同开发与运行方案.md` 为专项契约：Codex 负责项目群评估、架构与交接治理，DSH 负责具体开发测试，Hermes 承载项目产品 AI 能力与已接入范围的运行观测。交接目标为自动派发、回执、证据归集和异常升级，GPCF 保持唯一 Feature 与交付状态来源；架构取舍、高风险操作和验收状态仍按人工治理链裁决。该自动交接尚待端到端试点验证，不表示 25 个项目已完成接入。

## 3.2 业务架构：三条业务价值链和四类权威账

| 价值链 | 从需求到结果 | 主责与交接点 |
|---|---|---|
| 绿色供应链履约 | 客户/伙伴需求 → 平台订单与跨组织协同 → 单厂生产/质检/出库 → 运输和客户签收 → 对账、服务计量与复盘 | PVAOS 提供租户/组织/伙伴身份；GPC 持平台订单、运输与客户 POD；GFIS 持工厂工单、质量、库存和出库；PQC 持包装报价成本与审批；AaaS 持服务包、订阅、计量和 SLA。SOP 提供规则版本，WAME 审查治理证据。 |
| 世界资产服务化 | WAS 资产定义 → Ontology 语义 → XWAIL 机器契约/XAP 包 → WAME 注册授权发布 → World 世界状态/投影 → AaaS 服务化 → WAE 界面承载 | WAME 引擎 E1/E2/E3 仍按分期规划，不因 World 或 WAE 页面存在而宣称运行引擎已完成；CWME 是城市/园区/空间域实现，SpaceAI 是其场景应用及工程载体之一。 |
| 知识与决策 | 来源资料/业务证据 → KDS 正本与索引 → Brain/PKC 检索和工作台 → GCMEM 受控记忆 → ICP/AI 候选 → 人工复核与受权执行 | KDS 持知识正本和引用，业务事实仍由源系统持有；GCMEM 经唯一接口写长期记忆账本；ICP 只读投影与决策候选；XiaoC/XGD 生成或编排候选，XiaoG 仅按授权执行；WAME/人工作治理裁决。 |

| 权威账类别 | 唯一责任边界 | 允许其他项目持有的形态 |
|---|---|---|
| 业务事实 | GPC 平台订单/客户签收；GFIS 工厂执行/出库；PVAOS 租户组织伙伴；PQC 包装报价审批；AaaS 服务订阅计量 | 带来源 ID、版本、时间和用途的只读投影或证据引用 |
| 知识与记忆 | KDS 知识正本；GCMEM 为 KDS 体系内记忆账本的唯一受控写入口 | 检索索引、摘要候选和带出处的引用；不建立第二知识正本 |
| 治理与授权 | WAME 模型/资产治理、授权、发布及审计；GPCF 项目群方案、Feature、Evidence 和状态传导 | 项目本地门禁结果与请求回执；不得自审自批 |
| 研发协作 | GPCF 为交付状态权威；Project/Plane 为工作项与 Feature/Evidence 的只读协作投影 | 可编辑协作事项，但不能回写 GPCF 验收结论 |

客户 POD 与工厂出库回执必须分别建模：GFIS 发出工厂出库、质量与库存事件；GPC 依据运输/客户确认形成平台签收事实。跨厂库存和产能只在 GPC 建读模型，不向 GFIS 反写工厂主账。`KDS 是知识主存` 不等于 `KDS 是所有业务事实主存`。

## 3.3 系统架构：能力层、契约和关键路径

### 3.3.1 项目群数据管理架构

项目群采用“源系统持账、DRC 管目录、契约传数据、读模型供跨域查询、KDS 管知识、治理与业务确认分权”的联邦式数据管理架构。DRC 是资源发现与生命周期治理入口，不是集中业务数据库或默认数据湖；目录登记不代表数据复制、连接成功、访问获准或业务事实成立。`03-data-ai-knowledge/GlobalCloud绿色供应链体系数据治理模型.md` 和 `03-data-ai-knowledge/GlobalCloud绿色供应链体系系统-数据库边界总表.md` 细化绿色供应链数据流与数据库边界，`03-data-ai-knowledge/GlobalCloud项目群知识工程规范.md` 细化知识链；冲突时以本文主责边界和各源系统受控契约核对。

| 数据管理面 | 权威与职责 | 跨域输出及禁止事项 |
|---|---|---|
| 源数据面 | GFIS、GPC、PVAOS、PQC、AaaS、WAME、World、GPCF 等各持本域事务、模型、运行或交付状态；Edge 信号须经 GFIS 确证 | 源系统发布稳定对象 ID、版本化 API/事件及证据引用；其他项目不得直写其主账表 |
| 资源目录面 | DRC 登记数据库、数据集、事件、API、读模型和知识资源的元数据、责任人与生命周期 | 只发布资源描述、来源回链、准入条件和健康状态；默认不采集正文、凭据、生产样本或变更源端权限 |
| 交换与投影面 | 生产者持契约，消费者持自己的 Inbox/读模型；接口注册与跨服务身份由 MMC 等受控组件承接 | API、事件、Outbox/Inbox、批量受控导出均需版本、幂等、租户边界、错误回执和可回放证据；读模型不可反写源端 |
| 知识与智能面 | KDS 持知识正本与来源引用；GCMEM 经受控接口维护记忆账本；Brain/PKC/ICP/Agent 消费授权视图 | 索引、摘要、十一池投影及 AI 结果是派生或候选，不得冒充业务事实、知识正式版本或治理批准 |
| 治理与证据面 | 业务对象 owner 确认业务事实；WAME/人工裁决治理授权；GPCF 管架构、Feature/Evidence 与状态门禁 | DRC 记录申请与授权引用但不自授权限；证据确证不替代业务审批，项目群状态不由目录可见性提升 |

每项 DRC 目录记录的最小管理字段为：`resource_id`、资源类型、来源项目/系统与环境、业务 owner/数据 steward、源对象 ID 或定位引用、Schema/契约版本、更新方式、租户/组织/链/厂边界、密级或敏感标签、允许用途与授权引用、保留/删除责任、质量状态、血缘与证据引用、生命周期状态。DRC 只保存这些必要元数据；字段级样本、连接凭据、原始资料和生产数据由来源系统按授权另行管理。KDS 的 DSR-L0–L3 适用于对应知识资料，其他数据域的分级由各 owner 按适用规则确认，不把知识密级直接扩展为全项目群统一授权。

| 生命周期阶段 | 必须形成的记录与检查点 |
|---|---|
| 登记与分类 | 源项目确认主责、资源 ID、用途、敏感范围和目录可见性；缺 owner 或来源则保持 `candidate` |
| 契约与准入 | 生产者发布 Schema/API/事件版本、兼容规则、字段范围、租户边界；消费者提出用途，源 owner 与相应治理方确认授权 |
| 交换与使用 | 以 API、事件或受控导出读取，记录调用者、用途、源版本、时间、幂等键和审计回执；跨项目查询优先用只读投影 |
| 质量与追踪 | 源端对完整性、唯一性、时效性、一致性负责；投影端记录延迟、缺口和血缘，DRC 汇总目录质量状态但不替源端修事实 |
| 变更与退出 | 破坏性 Schema 变更先做影响分析、消费者兼容与回滚验证；到期保留、归档或删除由源 owner 执行并留回执，DRC 更新目录状态 |

数据管理职责按当前 28 项目分组承接，具体对象主责仍以 §4.1 和项目契约为准：

| 承接组 | 项目 | 数据管理检查点 |
|---|---|---|
| 业务与运行事实 | AaaS、WAME、GFIS、GPC、PVAOS、PQC、World、SpaceAI、SpaceAIStudio、PDC、SLC | 登记本域权威对象、owner、契约与保留责任；对外只输出授权范围内的引用或事实事件 |
| 知识与个人协同 | KDS、GCMEM、Brain、PKC | KDS 保持知识正本；记忆唯一写入口、索引和个人工作台均需来源回链与权限隔离 |
| 规范与控制 | WAS、XWAIL、SOP、MMC、GPCF | 分别管语义、机器契约、规则、可信调用和项目群门禁；不接管业务数据主账 |
| 入口与授权使用 | WAE、Studio、ICP、XiaoC、XGD、XiaoG、Project | 使用受控视图或受权 API；候选输出、执行回执和研发状态投影不得改写源端权威结论 |
| 资源目录 | DRC | 汇总前述资源元数据、质量/血缘状态与生命周期回执，不集中复制主账 |

首批实施按证据逐层推进：先盘点 28 项目的数据资源和责任边界，仅登记脱敏元数据；再选 GFIS→GPC 业务事件、KDS→Brain/ICP 知识读取等现有契约做离线目录与血缘样例；之后才在逐项授权下验证元数据采集、只读访问、质量告警与目录变更回执。每一步分别验目录正确性、权限隔离、来源回指、Schema 兼容、失效拦截和可回滚性。DRC 当前仍为 `bootstrap/partial`；真实数据库连接、生产数据迁移、共享权限写入及跨仓集成须在独立实施任务中验证和取得相应授权。

## 3.4 GlobalCloud Knowledge Engineering（GKE-001）

项目群将资料、会议、证据、关系、决策和长期记忆统一纳入一级工程 `GlobalCloud Knowledge Engineering`（`GKE-001`）。GPCF 是控制面，KDS 是知识事实主存，MMC 负责可信身份与跨服务授权，Brain 负责受控分析和候选生成，Studio 负责用户任务与人工复核，WAME、GFIS、GPC、PVAOS 等继续持有项目、订单、生产和资产等权威业务主数据。

`03-data-ai-knowledge/GlobalCloud项目群知识工程规范.md` 是 GKE-001 的项目群上位规范。任何系统不得建立平行资料、证据、审计或长期记忆主账；任何 AI 结果在确认前只能是 `candidate`；任何业务状态改变必须由业务对象 owner 独立授权。当前工程状态固定为 `active / partial / not_complete`，不得由文档、fixture、mock、组件测试或本地镜像提升。

`03-data-ai-knowledge/GlobalCloud知识工程应用体系实施方案.md` 是 GKE-001 的应用实施基线，负责把上位规范传导为 KDS、MMC、Studio、Brain 和 18 项目的分级产品交付、客户测试、运行证据与回滚路线；机器依赖由 `features/active/F-013-knowledge-asset-model-system/artifacts/gke-001-application-program-roadmap-v1.yaml` 控制，长期调度入口为 `02-governance/loop/GKE-001长期实施调度提示词.md`。客户只读试用、受控资料接入、候选复核和长期记忆必须按 Release 0 至 Release 3 逐级验收，不得跨级声明客户可用或生产就绪。
